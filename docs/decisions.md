# Decisions

## 1. Python environment: venv
All dependencies install with pip (pandas, scikit-learn, XGBoost), so conda adds nothing
essential. venv ships with Python and requirements.txt is the standard in software projects.
The environment lives in the project root and is excluded from Git.
[TO DO: the environment is called .env; rename it to .venv so it is not confused with the
python-dotenv secrets file]

## 2. Project structure
- dataset/raw_data: data exactly as downloaded from the API. Never modified.
- dataset/processed: data with renamed columns and new features. Regenerated by a script.
- src/pm: reusable code, installed with pip install -e . so it can be imported from anywhere.
  The src folder forces the use of the installed package.
- scripts: end-to-end steps (download.py, process.py).
- notebooks: exploration and experiments, numbered.
- results: figures, metrics and models. Excluded from Git.
- docs: problem statement, decisions and report.
Paths are defined once in config.py from __file__, so they work from any folder and on any
machine.
No .env file: there are no secrets, since the UCI API needs no key.

## 3. Download
The data is downloaded once with ucimlrepo and the complete original table (data.original)
is saved, including UID and Product ID. If the CSV already exists, it is not downloaded again.

## 4. Target: machine failure
I predict whether the process fails (339 positives, 3.39 %) rather than each failure mode
separately, since the modes have between 46 and 115 cases (RNF, 19). The mode columns are
used only to analyse which failures the model detects.

## 5. Main model: during the process
All inputs are used, including torque and process temperature, so that every deterministic
failure mode can be detected. The "before" model (without torque and process temperature)
is trained at the end as a comparison, to measure how much measuring torque is worth.
Assumption: torque and temperature readings are available at the start of the process. The
dataset gives one value per process and does not allow this to be checked.

## 6. Inconsistent rows: kept
There are 27 inconsistent rows: 9 failures with no mode flagged and 18 processes with
RNF = 1 but no machine failure. They are kept, and the label is machine failure as given.
The 18 RNF rows do not affect the target, because machine failure is 0 and that is correct.
Removing the 9 unexplained failures would make the model look better than it is: they are
exactly the cases that cannot be predicted, and they would keep happening in a real plant.

## 7. Discrepancies between documentation and data
- TWF: 46 cases in the data, versus 120 events (51 failures) in the description.
- RNF: 19 cases, versus 5.
- Maximum tool wear: 253 min, although tools should be replaced between 200 and 240 min.
- Rotational speed was "calculated from 2860 W", but the actual power is around 6280 W.
When the documentation and the data disagree, the data wins.

## 8. Column names
Columns are renamed to short names with no spaces or symbols and with units (air_temp_k,
torque_nm...). The mapping lives in config.py, and rename uses errors="raise" so it fails
immediately if a name does not match.

## 9. Tool cycles
Rows are a time sequence: tool wear forms a sawtooth against UID. Each tool life is a cycle,
detected when tool wear drops relative to the previous row (diff < 0, then cumsum). There
are 120 cycles, all start at zero wear, and the last one is incomplete (11 processes).

## 10. New features
- Temperature difference [K] = process − air (HDF).
- Power [W] = torque × rotational speed × π / 30 (PWF).
- Overstrain [min·Nm] = tool wear × torque (OSF).
Validation: the 95 processes with power outside [3500, 9000] W are exactly the 95 PWF
failures.
They are computed before splitting because each row uses only its own values, so there is no
leakage. Scaling and encoding Type do go inside the pipeline, because they use statistics
from the whole dataset.

## 11. Excluded features
UID (the model would learn the position in the list), Product ID (its useful information is
already in Type), tool_cycle (it is the grouping variable for splitting, not an input) and
the five failure modes (leakage: machine failure is their logical OR, and they are not known
at prediction time).
General rule: only use what is known at the moment the prediction is made.

## 12. Encoding Type: one-hot
It does not impose an order or distances between variants. The order L < M < H is real, but
the distances are not equal (tool wear per process is 2, 3 and 5 min). With three categories
it barely adds columns, and the same encoding is used in every model.
handle_unknown="ignore" so that an unseen variant does not break the model.

## 13. Data splits
Neighbouring rows are almost identical (same tool, temperatures following a random walk), so
the data is not split at random: it is split by whole cycles.

Main test set: 20 % of the cycles with StratifiedGroupKFold (stratified by machine failure,
grouped by tool_cycle, fixed seed).

| | Total | Test |
| --- | --- | --- |
| Processes | 10,000 | 1,951 (19.5 %) |
| Cycles | 120 | 24 |
| Failures | 339 | 65 (rate 3.33 % vs 3.40 % in training) |
| HDF / PWF / OSF / TWF / RNF | 115 / 95 / 98 / 46 / 19 | 22 / 16 / 23 / 9 / 0 |

Temporal test set (secondary): the last 24 cycles. Rejected as the main test set because it
has only 37 failures and no HDF: the temperature difference only drops below 8.6 K between
UID 3200 and 4900, and at the end of the dataset it stays between 10 and 11.5 K. It will be
used at the end to measure the effect of this drift.

Validation: 5-fold StratifiedGroupKFold on the training set, grouped by cycle.

## 14. The test set is frozen
It is not looked at or used for any decision until the final evaluation. Models,
hyperparameters and threshold are chosen with cross-validation.

## 15. Metrics
Models are compared with PR-AUC (average_precision), because it does not depend on the
threshold. Accuracy is useless: a model that always predicts "no failure" scores 96.6 %. A
random model has a PR-AUC equal to the failure rate, 0.034.
Configurations are compared fold by fold, since the 5 folds are identical across experiments.

## 16. Threshold criterion
Maximum recall with precision of at least 50 % (at most one false alarm per real failure).
This is an assumption in the absence of real costs. The threshold is chosen on validation,
never on the test set.

## 17. Success criterion
Recall of at least 75 % with precision of at least 50 % on the test set, and PR-AUC clearly
above logistic regression. Estimated recall ceiling around 83-90 %: there are 9 unexplained
failures, 1 failure caused only by RNF, and up to 46 TWF failures that are partly random.
A recall above 95 % would make me suspect leakage.

## 18. Baseline: logistic regression
Pipeline: StandardScaler on numeric columns and one-hot on Type, LogisticRegression with
max_iter=1000.

| Columns | class_weight | PR-AUC |
| --- | --- | --- |
| Basic | None | 0.464 ± 0.052 |
| Basic | balanced | 0.427 ± 0.055 |
| Basic + physical | None | 0.494 ± 0.045 |
| Basic + physical | balanced | 0.445 ± 0.041 |

- class_weight="balanced" lowers PR-AUC by about 0.04: None is used.
- Physical features improve the result in 4 of 5 folds and tie in the fifth.
- They help little because a linear model cannot represent risk at both ends of the power
  range (PWF), nor the "and" between temperature difference and speed (HDF).
Reference for the other models: 0.494 ± 0.045.

## 19. Tree models: random forest and XGBoost
Trees only look at the order of values (they split on thresholds), so numeric columns are
passed through without scaling. Type is still one-hot encoded.
Starting hyperparameters, not tuned: random forest with 300 trees; XGBoost with 300 trees,
learning_rate 0.1 and max_depth 4.

| Model | Basic | Basic + physical |
| --- | --- | --- |
| Logistic regression | 0.464 ± 0.052 | 0.494 ± 0.045 |
| Random forest | 0.742 ± 0.050 | **0.898 ± 0.042** |
| XGBoost | 0.746 ± 0.053 | 0.877 ± 0.033 |

- Trees far outperform logistic regression, as expected: they can split at both ends of the
  power range and combine conditions.
- Physical features add 0.13 to 0.16 PR-AUC to the trees, in all 5 folds. Domain knowledge
  improves the result about as much as switching to a more powerful model.
- Random forest and XGBoost tie: the difference (0.02) is smaller than the variation between
  folds (about 0.04), and XGBoost is untuned.
- Class weighting (class_weight="balanced", scale_pos_weight ≈ 28) ties or slightly lowers
  PR-AUC in every model: no weighting is used.
- Fold 5 is the hardest for every model.

## 20. Selected model and threshold
Random forest with basic + physical features, no class weighting, threshold 0.093
(maximum recall with precision of at least 50 %), chosen on out-of-fold predictions from
cross_val_predict.

| Threshold | Precision | Recall | Detected | Missed | False alarms |
| --- | --- | --- | --- | --- | --- |
| 0.050 | 0.380 | 0.923 | 253 | 21 | 413 |
| **0.093** | **0.507** | **0.883** | **242** | **32** | **235** |
| 0.100 | 0.525 | 0.876 | 240 | 34 | 217 |
| 0.200 | 0.722 | 0.861 | 236 | 38 | 91 |
| 0.300 | 0.844 | 0.847 | 232 | 42 | 43 |
| 0.400 | 0.931 | 0.832 | 228 | 46 | 17 |
| 0.500 | 0.957 | 0.814 | 223 | 51 | 10 |

- The original criterion from the problem statement is kept, prioritising not missing
  failures.
- Trade-off: moving from 0.093 to 0.3 would lose 10 failures but avoid 192 false alarms.
  With a cost-based criterion (for example, a missed failure costing 10 times a false alarm)
  the optimum would be around 0.3. The right threshold depends on the client's real costs.
- Risk: 0.093 lies where normal processes concentrate, so precision may vary on the test set.
- The threshold was chosen and evaluated on the same predictions, so these figures are
  somewhat optimistic. The frozen test set will confirm them.

This is the model that will be evaluated on the test set, unchanged.

## 21. Error analysis by failure mode (validation, threshold 0.093)
Only processes that are machine failures are counted in each row.

| Mode | Failures | Detected | Recall |
| --- | --- | --- | --- |
| HDF | 93 | 93 | 1.000 |
| PWF | 79 | 79 | 1.000 |
| OSF | 75 | 75 | 1.000 |
| TWF | 37 | 13 | 0.351 |
| RNF | 1 | 1 | 1.000 |
| No mode flagged | 8 | 0 | 0.000 |

- The three deterministic modes are detected at 100 %: the model has learned the generator's
  rules exactly.
- TWF is detected at 35 %: the failure time is random between 200 and 240 min.
- The single RNF failure is detected, most likely because it shares the process with another
  failure mode.
- None of the 8 unexplained failures is detected.
- The 32 missed failures are exactly 24 TWF plus 8 with no mode flagged.
- Conclusion: every error lies in the unpredictable part of the problem. The model is at the
  ceiling these data allow, so tuning or more complex models cannot improve recall; that
  would need new information (vibration, parts machined per tool).


## 22. Interpretation (cross-validation, training set only)
Computed with scripts/interpret.py on the selected model, refitted on each training fold.

Permutation importance: drop in PR-AUC on the validation fold when one input column is
shuffled (10 repeats), averaged over the 5 folds. Type is shuffled as one column.

| Feature | Drop in PR-AUC |
| --- | --- |
| rotational_speed_rpm | 0.218 ± 0.065 |
| temp_diff_k | 0.207 ± 0.068 |
| overstrain_min_nm | 0.200 ± 0.038 |
| power_w | 0.182 ± 0.049 |
| type | 0.057 ± 0.031 |
| tool_wear_min | 0.032 ± 0.006 |
| torque_nm, air_temp_k, process_temp_k | < 0.01 |

- The four top features are exactly the inputs of the deterministic rules: temperature
  difference and speed (HDF), power (PWF), overstrain (OSF). Speed ranks first because it
  takes part in two modes (HDF and power).
- Type matters only through OSF, whose overstrain limit depends on the variant.
- Raw torque and temperatures barely matter: their information is already inside the
  physics features, so shuffling one of them alone costs almost nothing.
- Tool wear has low importance because TWF happens at a random time between 200 and
  240 min, so it only signals a risk zone.

Partial dependence (mean predicted probability when one feature is set to a value in every
validation row):

| Feature | Behaviour |
| --- | --- |
| tool_wear_min | flat around 0.04 up to 200 min, then rises to about 0.24 |
| power_w | about 0.58 below 3500 W, about 0.04 in between, about 0.77 above 9000 W |
| temp_diff_k | about 0.12 below 8.6 K, drops to about 0.03 above it |

- The steps fall exactly on the generator's thresholds: the model has learned the rules.
- Caveat: changing power alone keeps torque and speed fixed, so some evaluated combinations
  cannot happen physically.

Missed failures: 32 (out-of-fold, threshold 0.093), exactly 24 TWF and 8 with no mode
flagged, as in section 21. The missed TWF have tool wear between 198 and 227 min; the 8
unexplained ones have any tool wear (20 to 210 min) and a probability close to 0. The list
is saved in results/metrics/missed_failures.csv.

## 23. Final evaluation on the frozen test set
The selected model (section 20) was trained on the whole training set and the test set was
predicted once, with threshold 0.093. Nothing was changed afterwards.

| | Cross-validation | Test |
| --- | --- | --- |
| PR-AUC | 0.898 ± 0.042 | **0.917** |
| Precision | 0.507 | **0.496** |
| Recall | 0.883 | **0.908** |
| Detected / missed / false alarms | 242 / 32 / 235 | 59 / 6 / 60 |

| Mode | Failures | Detected | Recall |
| --- | --- | --- | --- |
| HDF | 22 | 22 | 1.000 |
| PWF | 16 | 16 | 1.000 |
| OSF | 23 | 23 | 1.000 |
| TWF | 9 | 4 | 0.444 |
| RNF | 0 | - | - |
| No mode flagged | 1 | 0 | 0.000 |

Success criterion (section 17):
- Recall of at least 75 %: met (0.908).
- PR-AUC clearly above logistic regression: met (0.917 versus 0.494 ± 0.045 in
  cross-validation, more than 3 standard deviations above).
- Precision of at least 50 %: **not met** (0.496: 60 false alarms for 59 detected failures).

The criterion is therefore not met, by one false alarm. This was the risk noted in
section 20: 0.093 lies where normal processes concentrate, so precision is unstable. The
threshold is not moved after seeing the test set. PR-AUC, which does not depend on the
threshold, is within the cross-validation range.
- Every miss is again a TWF (5) or the unexplained failure (1).
- The test set has no RNF failures, so test recall may be slightly optimistic.

## 24. Secondary: temporal drift
Same model and threshold, trained on the first 96 cycles (8,112 processes) and evaluated on
the last 24 cycles (1,888 processes, 37 failures, no HDF). The training part includes
cycles of the main test set; nothing is decided with this experiment.

| | Main test | Last 24 cycles |
| --- | --- | --- |
| PR-AUC | 0.917 | 0.793 |
| Precision | 0.496 | 0.528 |
| Recall | 0.908 | 0.757 |
| Detected / missed / false alarms | 59 / 6 / 60 | 28 / 9 / 25 |

| Mode | Failures | Detected | Recall |
| --- | --- | --- | --- |
| PWF | 10 | 10 | 1.000 |
| OSF | 20 | 20 | 1.000 |
| TWF | 9 | 2 | 0.222 |
| No mode flagged | 2 | 0 | 0.000 |

- PR-AUC drops by about 0.12. The deterministic modes are still detected at 100 %; the drop
  comes from the mix of failures: there is no HDF (the temperature difference stays between
  10 and 11.5 K) and TWF is a larger share (9 of 37).
- In a plant, the conditions at the end of a period may differ from those used for
  training, so performance should be monitored and the model retrained.

## 25. Secondary: "before the process" model
Same model, main split, using only inputs known before machining starts: air_temp_k,
rotational_speed_rpm, tool_wear_min and Type. temp_diff_k, power_w and overstrain_min_nm
cannot be used because they depend on process temperature or torque. The threshold 0.093 is
kept; nothing was tuned for this model.

Cross-validation PR-AUC: **0.402 ± 0.039** (main model 0.898 ± 0.042), computed before
looking at its test result.

| | Main model | Before the process |
| --- | --- | --- |
| Test PR-AUC | 0.917 | 0.425 |
| Precision | 0.496 | 0.273 |
| Recall | 0.908 | 0.769 |
| Detected / missed / false alarms | 59 / 6 / 60 | 50 / 15 / 133 |

| Mode | Main model | Before the process |
| --- | --- | --- |
| HDF (22) | 1.000 | 1.000 |
| PWF (16) | 1.000 | 0.500 |
| OSF (23) | 1.000 | 0.913 |
| TWF (9) | 0.444 | 0.444 |

- Measuring torque and process temperature is worth about 0.49 of PR-AUC: without them the
  model is below logistic regression with all inputs.
- HDF is still detected at 100 % without process temperature. This is not physics: all 115
  HDF failures happen between UID 3237 and 4852, and in this dataset air temperature and
  temperature difference are strongly correlated (-0.70), a coincidence of two random walks.
  The model uses air temperature as a proxy for that period, which would not transfer to a
  real plant (see section 24).
